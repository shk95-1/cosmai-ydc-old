# 전체 흐름 — 수집에서 검색까지 무엇을 어떻게 했나

> 2026.08.24 · 김시현 (유튜브·시계열 파트)
> 이 문서는 "무엇을 만들었나"가 아니라 **"데이터가 어떤 손을 거쳐 결론이 됐나"** 를 순서대로 적은 것입니다.

**관통하는 원칙 하나.** 각 단계에서 **버리지 않고 표시**합니다. 빈 텍스트·중복 댓글·광고 영상·부분 수집을 지우지 않고 플래그로 남깁니다. 그래야 "빼면 결론이 어떻게 달라지나"를 나중에 물을 수 있습니다.

## 1. 수집 — 무엇을 어떻게 받았나

`youtube_collector.py`

| | |
|---|---|
| 경로 | YouTube Data API v3 (`channels.list` + `playlistItems.list`) |
| 왜 `search.list` 를 안 썼나 | 쿼터가 100배 비싸고 결과가 재현되지 않습니다 |
| 모집단 | 시드 채널 **43개** (고정 패널), 2023-07-01 이후 |
| 받은 것 | 영상 13,979편 + 그 영상의 댓글 |
| 저장 | 원본 JSONL 을 그대로 남기고, 그 옆에 정규화 CSV |

**원본을 지우지 않는 게 중요합니다.** 기획안 §4 — *"원천·수집 시각·변환 이력이 보존되지 않으면 결과를 재현하거나 검증할 수 없다."* 나중에 "태그를 넣으면 어떻게 되나"를 물을 수 있었던 것도 원본에 태그가 남아 있었기 때문입니다.

### 여기서 한 번 크게 틀렸습니다

처음 수집은 **채널당 상한 10편**이었습니다. 그 데이터로 월별 집계를 냈더니 매달 10건 근처가 나왔고, 그게 트렌드처럼 보였습니다. **상한이 곧 관측값이 된 것**입니다. 재수집했습니다.

이 경험이 뒤에서 두 번 더 쓰였습니다 — 커머스 랭킹의 관측 깊이 문제(§7), 그리고 팀원의 "수집기 고장과 시장 침체는 똑같이 0건" 지적이 같은 종류입니다.

## 2. 정제 — 무엇을 고치고 무엇을 표시만 했나

### 정규화는 한 함수만 씁니다

`trend.normalize_text` 하나입니다.

```
HTML 엔티티 해제  →  유니코드 NFKC  →  제어문자 제거  →  공백 축약
```

**소스마다 정규화가 다르면 소스 간 비교가 무의미해집니다.** 그래서 커머스·성분표·논문이 붙어도 이 함수를 씁니다. 실측으로 이 정규화가 주제 매칭 결과를 바꾼 경우는 영상 5,957편 중 3편(0.05%)뿐이었습니다. 그런데도 적용하는 이유는 두 가지입니다.

1. **중복 댓글 판정의 기준이 필요합니다.** 정규화 없이 비교하면 공백만 다른 복붙이 서로 다른 댓글로 남습니다(실측 2,395건 = 1.1%)
2. NAVER 블로그처럼 HTML 이 그대로 오는 소스에 같은 계약이 필요합니다

### 지운 것과 표시한 것

| 대상 | 처리 | 왜 |
|---|---|---|
| 빈 텍스트 | **표시** (`quality_flags=empty_text`) | 행을 지우면 분모가 흔들립니다 |
| 같은 영상 안 동일 댓글 | **표시** (`duplicate_in_parent`) | 복붙 스팸이 언급량을 부풀립니다 |
| 다른 영상의 같은 댓글 | **그대로 둠** | 각각 실제 반응입니다 |
| 쇼츠(60초 이하) | **분리** | 아래 참조 |
| 광고·협찬 | **표시만** | §7 에서 빼고 다시 계산해 비교 |
| 태그 | **본문에서 제외, 메타에 보존** | 아래 참조 |

### 쇼츠를 분리한 이유 — 숫자로

| | 쇼츠 | 장문 |
|---|---:|---:|
| 설명란 길이 중앙 | 0자 | 709자 |
| 주제 매칭률 | 13.1% | 64% |
| 분기별 비중 | **55% → 41% 로 움직임** | |

쇼츠와 장문을 한 분모에 넣으면 **포맷 선택의 변화가 주제 트렌드로 위장됩니다.** 그래서 분모는 장문만입니다.

### 태그를 뺀 이유

기획안 문장은 "제목+설명+태그"였는데 계산은 제목+설명만 씁니다. 태그를 넣으면 모집단이 **964 → 1,019편**이 되고 모든 구성비가 움직입니다. 그리고 태그로만 걸린 57편을 열어보니 올영하울·핸드크림·브이로그였습니다 — SEO 용 태그라 내용을 나타내지 않습니다.

태그는 `source_metadata.tags` 에 보존돼 있어 재수집 없이 결정을 바꿀 수 있습니다.

### 성분표 정제 — 두 사람이 각자 하고 합쳤습니다

수호님이 식약처 × 올리브영을 매핑해 주신 CSV 입니다. 원본 30,097행 / 577제품.

**같은 문제를 양쪽에서 봤고, 숫자가 갈렸습니다.**

| | 뭉친 셀 탐지 | 복구 |
|---|---|---|
| 우리 `normalize_ingredients.py` | **28건** (제품 단위 최댓값 40자 초과) | 6건 성공, 22건은 "집계에서 제외할 것" 표시 |
| 수호님 `step06_ingredient.py` 초판 | 21건 (제품 행수 5개 이하) | 21건 전부 |

**우리 28건이 맞았고 그의 21건이 부분집합이었습니다.** 그가 셀 단위로 다시 스캔해
7건을 더 찾았고, 최종 분류가 이렇게 나왔습니다.

| 유형 | 건수 | 처리 |
|---|---:|---|
| A. 제품 전체가 1행 (완전 뭉침) | 21 | 자동 복구 |
| B. 정상 행 사이 셀 하나가 오염 (성분 + 각주) | 5 | 자동 복구 |
| C. 색상 2종 전성분이 이어붙음 (크리니크) | 2 | **원본 유지** |

C 는 두 색상의 전성분이 헤더 텍스트를 끼고 붙어 있어 자동으로는 못 자릅니다.
**잘못 자르는 것보다 안전하다고 판단해 남겼습니다** — 우리가 22행에 "제외할 것"을
표시한 것과 같은 판단입니다.

그가 남긴 기록 중 이게 중요합니다 — 길이만으로 스캔했을 때 39건이 걸렸는데
대부분이 **정상적으로 긴 INCI명**이었습니다.

```
펜타에리스리틸테트라-다이-t-부틸하이드록시하이드로신나메이트   ← Irganox 1010, 정식 INCI명
피토스테릴/이소스테아릴/세틸/스테아릴/베헤닐다이머디리놀리에이트   ← 왁스류 유화제, 정식 INCI명
```

**자동 복구가 정상 데이터를 망칠 수 있다는 걸 먼저 확인하고 기준을 좁혔습니다.**

결과가 `product_ingredient_function_repaired.csv` 입니다 — **31,246행 / 577제품 /
40자 초과 성분명 0건.** 이걸 정본으로 `data/external/` 에 두었고, 이전 판(30,097행)을
대체합니다.

### 커머스 랭킹 정제 (`commerce_ranking.py`)

석현님 수집기가 PostgREST 서버에 쌓는 `rank_snapshot` 입니다. 네 소스
(oliveyoung · glowpick · daisomall · hwahae) 6일치 · 시간당 스냅샷이고
정지 시각(08-24 00:00) 이전 **169,053행**입니다.

**정제할 게 데이터가 아니라 받는 방법이었습니다.**

처음엔 정렬 없이 `limit/offset` 으로 받았습니다. 그 결과 **완전 중복 37%(62,812행)**
와 **관측 깊이 22~100위 변동**이 보였고, 저는 그걸 수집 파이프라인 문제로 보고
석현님께 알렸습니다. **둘 다 서버에 없는 현상이었습니다.**

현준님이 자기 사본에서 재현이 안 된다며 원인을 짚어 주셨습니다 — 페이징 표류입니다.
Postgres 는 `ORDER BY` 가 없으면 순서를 보장하지 않고, 그 위에 수집기가 계속
쓰고 있었습니다. 그래서 같은 offset 이 다른 행을 가리켰습니다.

- 같은 행이 여러 번 들어옴 → **중복으로 보임**
- 다른 행은 통째로 빠짐 → 스냅샷이 얕게 보임 → **깊이 변동으로 보임**

확인은 두 단계였습니다. 중복 예시로 든 슬라이스를 직접 조회하니 **1행**이었고,
정지 집합을 전순서 정렬해 다시 받으니 **중복 0건 · 보드 22개 중 21개 깊이 고정**
(oliveyoung suncare 는 85개 스냅샷 전부 100위)이었습니다.

**그래서 추출에 세 가지를 걸었습니다.**

| | 왜 |
|---|---|
| `captured_at < freeze` 로 작업 집합 정지 | 페이징 중 유입을 막습니다 |
| 유일 키로 전순서 정렬 | 순서를 보장합니다 |
| **받은 행수를 서버 `count=exact` 와 대조** | 어긋나면 멈춥니다 |

**세 번째가 핵심입니다.** 정지·정렬만 해도 대개 맞지만, **행수를 대조하지 않으면
다음에 또 조용히 틀립니다.** 제가 그걸 안 해서 잘못된 이슈 보고를 했습니다.

이건 이 문서 §1 의 "수집 상한 10" 과 같은 계열의 실패입니다. 그때는 **수집 상한**이
관측값이 됐고, 이번엔 **추출 방법**이 관측값이 됐습니다. 둘 다 파이프라인이 조용히
답을 만들어 낸 경우입니다. 그래서 **행수 대조 같은 자기 검사를 코드에 박아 두는
것**이 문서에 적어 두는 것보다 낫습니다.

현준님이 같은 함정의 다른 얼굴을 하나 더 알려주셨습니다. 정지·정렬을 다 해놓고도
**80,102행 중 80행을 잃은** 적이 있다고요 — PostgREST 가 마지막 행을 개행으로
끝내지 않는데 CSV 페이지를 그냥 이어붙이면 **경계마다 두 레코드가 한 줄로 붙습니다.**
오류는 안 납니다. 우리 코드는 JSON 으로 받아 페이지마다 파싱하므로 이 함정은 없지만,
**행수 대조는 이것도 잡습니다.** 어떤 방식으로 틀리든 개수는 안 맞기 때문입니다.

그리고 판별법 하나를 얻었습니다 — **수집기 버그는 소스마다 다르고, 추출 버그는
스트림 전체에 균일하다.** 저는 "네 소스가 정확히 37%"를 공통 원인의 증거로 읽었고
현준님은 같은 신호를 추출 문제의 증거로 읽었습니다. 그가 맞았습니다.

**가장 값진 지적은 이것입니다** — *"프로모션이 랭킹을 미는 구조라면 그 자체가
결과인데, 아티팩트로 지웠으면 놓쳤을 겁니다."* 제가 잘못 지운 건 중복이 아니라
**결과 하나**였습니다. 데이터를 의심하는 것과 결과를 지우는 것은 다릅니다.

## 3. 공통 스키마 — 소스를 붙일 수 있게 만드는 지점

`to_common_schema.py`

5계층입니다. 팀 합의 사항입니다.

```
raw_record          원본 그대로
document            문서 하나 = 한 행   ← 여기가 결합 지점
mention             (문서, 주제) 쌍
entity_link         문서 ↔ 제품 연결   (PoC 에서 미완)
topic_daily_metric  집계
```

`document` 의 칸은 이렇습니다.

```
doc_id · source · source_item_id · content_type · parent_item_id ·
channel_id · published_at · url · text · quality_flags · source_metadata
```

**`source` 를 하드코딩하지 않는 것이 핵심입니다.** 그래서 커머스·논문·NAVER 가 같은 스키마로 변환되면 **행이 늘어나는 것뿐이고 뒤의 코드가 안 바뀝니다.** 실제로 BM25·청크 생성기·평가기 모두 `source` 를 읽어서 씁니다.

현재 유튜브 변환 결과입니다.

| | |
|---|---:|
| document | 261,317행 |
| mention | 105,358행 |
| channel | 43행 |

검증 삼종(재현 시 반드시 같아야 하는 값): **선크림 장문 964편 / 댓글 60,348건 / 중복 제외 60,311건**

## 4. 지표 — 트렌드를 무엇으로 봤나

`trend.py`

### 빈도를 직접 쓰지 않습니다

이게 이 파트의 가장 중요한 결정입니다. 유튜버 설명란 길이 중앙값이 3년간 **1,253자 → 709자(−44%)** 로 줄었습니다.

| | 문서 기준 비율 | **구성비** |
|---|---:|---:|
| 13주제 변화량 합계 | **−28.6%p** | −0.0%p (정의상 0) |
| 하락한 주제 수 | **10 / 13** | 6 / 13 |

문서 기준으로 보면 **13개 주제 중 10개가 "사라짐"** 이 됩니다. 트렌드가 아니라 유튜버들이 설명을 짧게 쓰기 시작한 것입니다.

```
구성비 = 그 주제 언급 문서 수 ÷ 그 기간 전체 주제 언급 문서 수
```

분자와 분모가 같이 줄어 드리프트가 상쇄됩니다.

### 비교는 전년 동분기(YoY)

선크림은 계절 상품입니다. 장문 중 선크림 언급 비중이 **3년 연속 Q2 최고**(26.7 / 25.3 / 25.6%)입니다. 인접 분기를 비교하면 매년 Q2 에 급상승, Q4 에 사라짐이 나옵니다.

### 영상과 댓글을 합치지 않습니다

둘이 다른 것을 측정합니다.

| 주제 | 영상 설명 | 댓글 |
|---|---|---|
| SPF | 11/13분기 | 9/13 |
| **백탁** | **0/13분기** | **12/13** |

가중합으로 섞으면 **"소비자는 불만을 말하는데 제작자는 안 다루는 주제"** 라는 신호가 사라집니다. 그래서 나란히 두고, 그 차이를 `gap`(댓글 − 영상)으로 씁니다. **`gap` 이 제품 공백 신호입니다.**

### 나머지 지표

| 지표 | 정의 |
|---|---|
| `persistence` | 최근 4분기 중 구성비가 그 주제의 전체 기간 중앙값을 넘는 분기 수 |
| `channel_diffusion` | 고유 채널 수 50% + 채널 분포 엔트로피 50% |
| `evidence_strength` | 유효 근거 수 43.75% + 고유 채널 수 31.25% + 비중복 비율 25% |

`channel_diffusion` 에 엔트로피를 넣은 이유는 비율만 보면 "3채널이 골고루"와 "1채널이 몰아서"를 구분하지 못하기 때문입니다.

## 5. 판정 — 임계값을 어떻게 정했나

`judge.py`

```
근거 부족   evidence_strength < 50  또는  document_count < 5
신규 등장   직전 3분기 구성비 < 1%  &&  현 분기 문서 ≥ 5  &&  채널 2개 이상
단기 피크   velocity > +τ  &&  persistence = 1
급상승      velocity > +τ  &&  persistence ≥ 2
채널 확산   channel_diffusion 전년 동분기 대비 +0.089 초과  &&  velocity ≤ +τ
지속 인기   |velocity| ≤ τ  &&  persistence ≥ 3
사라짐      velocity < −τ  &&  현 분기 구성비 < 최고 분기의 절반
```

**임계값을 실측 분포에서 뽑았습니다.**

| 임계값 | 값 | 어떻게 |
|---|---|---|
| `τ` | **0.35** | 실측 YoY 분포 75분위. 영상 0.366 · 댓글 0.358 로 두 소스가 독립 계산인데 거의 일치 |
| `DIFFUSION_TAU` | **0.089** | 같은 방법 — 전년 동분기 변화량 234셀의 절대값 75분위 |

**한 번 뽑아 고정하고 분기마다 재계산하지 않습니다.** 재계산하면 아무 변화 없는 분기에도 상위 25%가 급상승으로 찍힙니다. 그리고 **소스마다 다시 뽑아야 합니다** — 지금 값은 유튜브 실측치입니다.

### 채널 확산 임계값은 한 번 조였습니다

처음엔 "0보다 크면 상승"이었습니다. 그랬더니 판정된 89셀 중 **52셀(58%)** 이 채널 확산으로 쏠렸습니다. 유형이 한 곳에 몰리면 분류의 정보량이 없습니다. 실측 75분위로 조이니 52 → 14셀이 되고, 남은 것은 +0.10 ~ +0.54 의 실제 도약이었습니다.

**혼합자차는 제품의 32.9% 인데 댓글 구성비가 1.21% 입니다.** 우리가 표본 부족으로 판정 보류한 주제인데, 제품이 없어서가 아니라 **아무도 그 이름으로 말하지 않기 때문**이었습니다. 반대로 무기자차는 제품 비중이 가장 낮은데 담론은 1위입니다.

### 커머스 랭킹이 붙어서 시간축이 셋이 됐습니다

석현님 랭킹이 6일치가 되면서 소스 구성이 바뀌었습니다.

| 소스 | 시간축 | 무엇을 보나 |
|---|---|---|
| 식약처 | 18년 (전수) | 공급측 — 제조사가 무엇을 언제 내놨나 |
| 유튜브 | 13분기 | 수요측 담론 — 무엇이 더 논의되나 |
| **커머스 랭킹** | **6일 · 시간당** | **성과 — 무엇이 지금 순위에 오르나** |
| 커머스 리뷰 | 단일 시점 | 사용 감각 (작성일 편향이 있어 점유율만 해석) |

`MASTER_REPORT` §3-1 이 트렌드를 횡단면으로 재정의한 근거가 *"랭킹 스냅샷이
2.7일뿐"* 이었습니다. 그 전제가 바뀌었고, 수집기가 계속 돌고 있어 발표일에는
8일치가 됩니다.

**다만 커머스에 우리 판정 규칙을 쓰면 안 됩니다.** 유튜브 지표는 전년 동분기
비교이고 계절성을 상쇄하려고 그렇게 만들었습니다. 6일에 같은 규칙을 쓰면
의미가 없습니다. 커머스가 답하는 질문은 다릅니다 — **"지금 무엇이 오르고
있나"** 입니다. 그래서 판정 유형(급상승·사라짐)을 붙이지 않고 순위 이동만
그대로 냅니다.

### 제품 단위 조인은 하지 않았습니다

성분표 ↔ 유튜브·커머스 제품명을 잇지 않았습니다. 팀에서 **세 사람이 독립적으로 같은 벽**에 부딪혔습니다.

| 누가 | 결과 |
|---|---|
| 팀원 (매처) | 100개 중 **38개** |
| 석현님 MASTER_REPORT | 정확일치 **119/577 (20.6%)**, 퍼지매칭은 오매칭으로 폐기 |
| 우리 | 시도하지 않음 |

원인도 확인됐습니다 — 올리브영 상품의 상당수가 `기획/N종 택1` **묶음 페이지**입니다. 제품 하나가 아니라 진열대입니다. 성분표에서도 성분 100개 넘는 제품이 21개(최대 385행)였습니다.

**조인율을 억지로 올리면 틀린 성분–반응 연결이 분석 전체를 오염시킵니다.** 낮은 조인율을 인정하고 각 소스를 독립 축으로 씁니다.

## 7. 검증 — 결론이 얼마나 버티나

여기가 이 파트에서 가장 공들인 부분입니다. **판정기와 채점기를 따로 만들었습니다.**

| 검증 | 스크립트 | 결과 |

| 재실행 일치 | `reproduce.py` | 커밋된 338행 **전부 재생성**. 버그 1건 발견 |

### 광고 — 빼도 안 빼도 손실입니다

선크림 장문 964편 중 **465편(48.2%)이 광고·협찬**입니다. 신고 필드(`has_paid_product_placement`)는 254편뿐이고 설명란 문구로 407편이 걸립니다 — **신고만 믿으면 절반을 놓칩니다.**

빼면 판정 64셀 중 **19셀 뒤집히고 24셀이 표본 미달로 사라집니다.** 그래서 빼지 않고 **필터 민감으로 표시**합니다. 464편을 버리면 13주제 중 절반이 판정 불가가 되어 도구가 아무 말도 못 합니다.

### 재현성 검사가 버그를 잡았습니다

같은 run 디렉터리를 실수로 두 번 넘기면 `raw` 카운트만 두 배가 되어 `unique_ratio` 가 절반으로 떨어졌습니다. 문서 수는 안 늘어나는데 비중복 비율만 망가지는 — **조용히 틀리는 종류**입니다. 댓글을 `comment_id` 로 한 번만 세도록 고쳤습니다.

그리고 **정본 run 이 확정됐습니다.** `data/panel` 두 개입니다.

### 오류 주입 — 429 와 403 의 구분

기획안이 지정한 것을 그대로 주입했습니다. 가장 중요한 건 **429(rate limit)와 403(quotaExceeded)의 구분**입니다. 429 는 기다렸다 다시 걸어야 하지만 403 은 하루가 지나야 풀립니다. 둘을 같이 다루면 남은 쿼터를 태우며 3번 더 부릅니다. 코드에 그 구분이 실제로 있었습니다.

### 후향 검증 — 가장 불편한 결과

과거 분기까지만 알고 있었던 것처럼 지표를 다시 계산해 판정하고, 그 뒤 4분기를 봤습니다. `persistence` 의 기준선이 전체 기간 중앙값이라 자르지 않으면 **미래를 보고 판정**하게 됩니다. 그래서 `CUTOFF_QUARTER` 훅을 넣었습니다.

| 기준 | 질문 | 적중 | 기저율 |
|---|---|---:|---:|
| A | 판정 후에도 계속 올랐나 | **27%** | 47% |
| B | 올라간 수준이 유지됐나 | **64%** | 47% |
| A (상승 계열 9건) | | **22%** | 47% |

**우리 지표는 서술 도구이고 예측 도구가 아닙니다.** 13분기 · 계절 상품 · 964편으로는 예측 모델을 세울 수 없습니다. 기획안도 *"표본이 충분할 때만 후행 지표 예측을 시도하고, 부족하면 통계 baseline 으로 대체"* 라고 적어 뒀고, 부족한 쪽이 맞았습니다.

**기저율을 같이 낸 것이 중요합니다.** 적중률만 내는 후향 검증은 검증이 아니라 홍보입니다.

> 팀의 ML 파트도 독립적으로 같은 곳에 도달했습니다 — 모델 A 가 persistence baseline 상대로 9판 6승 3패, 모델 E(논문 수 → 매출)는 넣으니 오히려 나빠졌습니다.

## 8. 청크 — 임베딩에 넣을 단위를 만드는 곳

### 나누는 지점을 여기로 정했습니다

인코딩(벡터 만들기)은 **한 사람이 전체를 한 번에** 돌립니다. 이유가 있습니다.

- **TF-IDF/SVD 는 애초에 나눌 수 없습니다.** 코퍼스에 학습되는 방식이라 두 사람이 각자 fit 하면 코드가 똑같아도 서로 다른 좌표계가 나옵니다
- 사전학습 모델은 나눌 수 있지만, 모델 리비전·프리픽스·L2 정규화·dtype·텍스트 정규화·입력 필드 **여섯 개가 전부 같아야** 합니다. 하나만 어긋나면 **오류 없이** 엉뚱한 결과가 나옵니다
- 전체 28만 청크를 GPU 로 돌리면 10~30분입니다. **나눠서 얻을 시간이 없습니다**

대신 **"뭘 한 덩어리로 볼지"는 그 소스를 아는 사람만 정할 수 있으므로** 소스별로 나눕니다.

### 계약은 다섯 칸입니다

```
chunk_id · doc_id · source · ordinal · text
```

`doc_id` 가 공통 스키마의 그것이라 **합치기가 join 이 아니라 이어 붙이기**가 됩니다. 합칠 게 없으니 못 합칠 일도 없습니다.

### 소스별 규칙

| 소스 | 한 청크 | 결과 |
|---|---|---|
| 유튜브 댓글 | 1건 = 1청크 (중앙 48자) | 252,332 |
| 유튜브 영상 | 제목+설명, 500자에서 분할 | 26,584 |
| **커머스 리뷰** | 1건 = 1청크 (중앙 74자) | **18,476** |
| 성분 — 제품 요약 | 브랜드 + 자차 방식 + 고함량 성분 | 577 |
| 성분 — 전성분 | 순번 붙인 전성분 (`1.정제수, 2.…`) | 1,543 |
| 성분 — 성분 단위 | 성분 + 보급률 + 평균 배합순위 | 1,931 |
| **식약처 원부** | 품목 + 업체 + 보고일자 + 차단지수 + 효능효과 | **4,735** |

### 커머스 리뷰가 빠져 있었습니다

처음 청크에는 유튜브와 성분만 있었습니다. **임베딩의 값이 "이름 없는 불만을
찾는 것"인데, 그 불만이 가장 많이 적힌 곳이 대상에서 빠져 있었습니다.**

현준님이 `review_topic`(14,232행)을 재서 이걸 드러냈습니다. 그 테이블은 사이트가
제공한 **객관식 보기**입니다 — `topic_name` 이 "복합성에 좋아요" 같은 것이고
`sentence` 가 전부 비어 있습니다. 행 수가 392/392/392, 301/301/301 로 정확히 같은
것도 그 증거입니다. 체크박스지 발화가 아닙니다.

진짜 불만은 자유 텍스트에만 있습니다. 리뷰 본문 19,807건 실측입니다.

| 표현 | 리뷰 본문 | `review_topic` |
|---|---:|---:|
| **백탁** | **552** | **0** |
| 따가 | 266 | 0 |
| 눈시림 | 252 | 0 |
| 하얗게 | 79 | 0 |
| 겉돌 | 61 | 0 |

우리가 "커머스 백탁 12.09%"를 찾은 이유가 이것입니다. 객관식만 보면 **백탁은
존재하지 않는 문제**입니다.

**500자 근거**: `multilingual-e5-base` 상한이 512토큰이고 한국어는 대략 1.5자가 토큰 하나입니다. 500자면 약 330토큰이라 여유가 있습니다. 상한을 꽉 채우면 모델을 바꿀 때 다시 쪼개야 합니다.

**겹침(overlap)은 두지 않았습니다.** 겹치면 같은 문장이 여러 청크에 들어가 검색 상위가 한 문서로 채워집니다. 우리는 근거를 **여러 문서에서** 모아야 하므로 중복이 더 해롭습니다.

### 검증기를 같이 만들었습니다

```bash
python chunks.py --validate reports/chunks_상대.csv
```

28만 문서를 GPU 로 태운 다음 `doc_id` 가 어긋난 걸 알면 처음부터 다시입니다. 그래서 **인코딩 전에** 걸러야 합니다. 위반 11종을 잡는지 자체 점검에 넣었습니다 — 통과만 하는 검증기는 장식입니다.

### 성분·식약처 청크는 수호님 것을 정본으로 했습니다

제가 만든 것과 수호님이 만든 것이 두 벌이었습니다. **수호님 쪽으로 정했습니다** —
`taxonomy.py` 에서 나오는 자차 방식·기능성 분류가 있고, 우리에게 대안이 없는
**식약처 4,735건**이 들어 있습니다.

다만 계약을 두 곳에서 어겨서 `repair_chunks.py` 로 후처리했습니다.

| 위반 | 규모 | 왜 문제인가 |
|---|---:|---|
| 정규화 누락 | 215행 | 제품명의 이중 공백. 같은 제품이 다른 토큰열이 됩니다 |
| **`doc_id` 충돌** | 2,120행 | `formula_summary` 와 `formula_full` 이 같은 `PROD:제품명` 을 써서 한 문서에 `ordinal` 이 `[0,0,1,2]` 로 들어갑니다 |

두 번째가 실질적입니다. 계약 위반보다 나쁜 건 **근거 추적이 깨지는 것**입니다 —
`doc_id` 로 되짚었을 때 요약인지 전성분인지 알 수 없습니다.

**본문은 정규화 외에 건드리지 않았습니다.** 성분명 잡음(`ING:000ppm함유`)도
남겼습니다 — 여기서 지우면 그가 생성기를 고칠 때 무엇이 문제였는지 알 수 없습니다.

### (참고) 제가 만들었던 성분 청크

유튜브는 공통 스키마에 `doc_id` 가 있지만 **성분표에는 없습니다.** 그래서 `chunks.py` 를 성분표에 그냥 돌릴 방법이 없습니다(돌리면 유튜브가 나옵니다 — 실제로 그런 일이 있었습니다).

`ingredient_chunks.py` 가 `doc_id` 규칙을 정합니다.

```
ingredient_product:{제품명 sha1 앞 12자}
ingredient_term:{성분명}
```

그리고 **묶음 페이지를 걸렀습니다.** 고유 성분 80개 초과는 여러 SKU 가 섞인 페이지로 보고 채택 통계에서 뺍니다.

교차 확인: 나이아신아마이드 채택률이 **69.4%(540개 중 375개)** 로 나왔고, 석현님 MASTER_REPORT 의 **68.3%**(577 분모)와 사실상 일치합니다.

## 9. 검색 — 어휘 검색을 먼저 만든 이유

`bm25.py` · `retrieval_eval.py`

### 벡터보다 이걸 먼저 만들었습니다

임베딩 모델을 뭘로 정하든 **어휘 검색 기준선은 안 바뀝니다.** 기준선 없이 하이브리드를 만들면 "합친 게 더 낫다"를 확인할 방법이 없습니다. 후향 검증에서 기저율을 같이 낸 것과 같은 이유입니다.

### 둘이 반대로 약합니다

```
질의: "에칠헥실트리아존"
  BM25 → 그 문자열이 있는 문서를 정확히 찾는다
  벡터 → "화학 성분 이름 같은 것"이랑 다 비슷하다고 본다
         (에칠헥실메톡시신나메이트도 비슷하다고 나옴 — 성분이 다른데)

질의: "하얗게 떠서 싫다"
  BM25 → 못 찾는다. "백탁"이라는 글자가 없다
  벡터 → 찾는다. 뜻이 가깝다
```

실측입니다. 26만 문서 색인, `"하얗게 떠서 싫다"` 상위 5건 — **다섯 건 모두 백탁 얘기이고 다섯 건 모두 "백탁"이라는 단어가 없습니다.**

### 평가기 — 정답이 공짜로 있습니다

`common/mention.csv` 가 (문서, 주제) **105,358쌍**입니다. `match_topics()` 가 만든 것이라 사람이 라벨을 달 필요가 없습니다.

| 모드 | 질의 | 정답 | 목적 |
|---|---|---|---|
| `literal` | 별칭 하나 | 그 주제 문서 전부 | **고장 감지** |
| `heldout` | 별칭 A | A 의 토큰이 없는 같은 주제 문서 | **벡터가 넘어야 하는 바닥선** |

| 모드 | P@10 | MRR@10 | Hit@10 |
|---|---:|---:|---:|
| `literal` (고침 전) | 0.754 | 0.799 | 87% |
| `literal` (고침 후) | **0.862** | **0.907** | **93%** |
| `heldout` | **0.000** | 0.000 | 0% |

(이 값은 성분 사전을 얹기 전입니다. 얹은 뒤 0.828 로 내려가는데 이유는 §9-비교에 있습니다.)

**`heldout` 0.000 은 측정이 아니라 정의입니다.** 정답을 "질의 토큰이 없는 문서"로 잡았으니 토큰이 겹치는 문서만 점수를 매기는 어휘 검색은 구조적으로 0 입니다. 발견이 아니라 **바닥선**이고, 벡터가 0 을 넘기면 그게 임베딩이 기여한 몫입니다.

### 평가기가 고장 셋을 잡았습니다

`literal` 을 고장 감지용으로 만들었는데 실제로 잡았습니다. **셋 다 에러가 안 나고 결과만 조용히 빕니다.**

근본 원인은 하나입니다 — **`topics.py` 는 부분문자열로 매칭하고 색인은 형태소로 나눕니다.**

```
신제품   → ['제품']        신 이 접두사로 떨어진다
화학적   → ['화학']        적 이 접미사로 떨어진다
차단지수 → ['차단','지수']  둘로 갈린다
제형     → []             제(접두) + 형(한 글자) 로 전멸한다
```

`제형` 이 빈 결과인 건 평가 문제가 아니라 **검색 결함**입니다. 그리고 고치는 과정에서 반대 방향 함정도 나왔습니다 — 별칭을 전부 명사로 등록하니 `하얗게`·`하얘` 가 서로 다른 토큰이 됐습니다(전에는 둘 다 `하얗`). **활용형을 명사로 박으면 형태소 통합이 깨집니다.** 그래서 등록 대상을 Kiwi 에게 물어서 고릅니다.

부수적으로 `add_user_word` 에 score 를 안 주면 **등록해도 조용히 무시된다**는 것도 확인했습니다.

## 9-비교. 벡터를 붙이고 셋을 같은 기준으로 재봤습니다

`multilingual-e5-base`(리비전 `d1287505…`) · 768차원 · L2 정규화 · float32.
유튜브 + 커머스 리뷰 **297,392청크**를 RTX 4060 에서 인코딩했습니다(913MB).

**성분·식약처는 인코딩하지 않았습니다.** `에칠헥실트리아존` 을 벡터에 넣으면
`에칠헥실메톡시신나메이트` 도 비슷하다고 나옵니다. 성분이 다른데 비슷하다고 하면
**순위 문제가 아니라 오답**입니다. 그쪽은 BM25 가 맡습니다.

| 모드 | bm25 | vector | hybrid |
|---|---:|---:|---:|
| `literal` P@10 | **0.828** | 0.567 | 0.710 |
| `literal` Hit@10 | 93% | 89% | **98%** |
| `heldout` P@10 | **0.000** | **0.042** | 0.032 |
| `heldout` Hit@10 | 0% | **17%** | 13% |

**08.25 재측정 — 수호님 2차 청크 반영 후.** mfds 4,735건에 `보고번호 · 품목번호`
접두가 붙어 텍스트가 바뀌었고, 벡터를 다시 합쳤습니다. 위 표는 그 **전**입니다.

| 모드 | bm25 | vector | hybrid |
|---|---:|---:|---:|
| `literal` P@10 | 0.828 → **0.841** | 0.567 → **0.541** | 0.710 → **0.662** |
| `heldout` P@10 | 0.000 | 0.042 → **0.038** | 0.032 → **0.028** |
| `heldout` Hit@10 | 0% | 17% → **13%** | 13% → **10%** |

**하이브리드는 다시 재고 넣었다.** 처음엔 이 표에 08.24 값이 남아 있었다 —
한 표에서 다른 시점을 비교하고 있었다. 결론은 안 바뀌고 **오히려 벌어졌다**:
어휘는 BM25 에 0.179 지고 의미는 벡터에 0.010 진다.

벡터가 내려간 이유를 **쟀습니다**. 접두어 30자가 4,735청크에 똑같이 붙어 그 덩어리가
서로 비슷해졌고, `heldout` 상위10에서 mfds 가 차지한 칸이 **23 → 28** 로 늘었습니다
(3.8% → 4.7%). heldout 정답은 유튜브·커머스 문서뿐이라 그 칸은 전부 헛것입니다.
옛 벡터를 되살려 직접 비교한 값입니다 — 추측이 아닙니다.

**교환이고 결함이 아닙니다.** 얻은 것은 식약처 4,735건이 서로 구분된다는 것입니다
(같은 이름 20그룹이 이제 보고번호로 갈립니다). 대응은 지표를 고치는 게 아니라
**소스로 갈라 쓰는 것**입니다 — 담론 질의에 식약처를 뒤지는 건 범주 오류입니다.

### 임베딩은 채택 기준을 넘었습니다

기준을 **미리** 정해 뒀습니다 — `heldout` 에서 BM25 는 구조적으로 0.000 이므로
(정답을 "질의 토큰이 없는 문서"로 잡았으니) **0을 넘느냐**가 기준입니다.
결과를 보고 기준을 만들면 그건 성능이 아닙니다.

벡터가 **0.042 · Hit 17%** 입니다. 60개 질의 중 10개에서 **글자가 하나도 안 겹치는
문서를 찾았습니다.**

**이긴 자리가 명확합니다.** 점수의 대부분이 두 질의에서 나옵니다.

```
톤 업    P@10 1.00   ← 상위 10건 전부 정답
눈 시림  P@10 0.60
나머지 8개 주제       0.10~0.20
```

둘 다 **공백이 든 별칭**입니다. BM25 는 토큰화하면 조각나서 0점인데 벡터는 문장
그대로 이해합니다. 나머지도 8개 주제에 흩어져 있어 한두 주제에 몰린 것은 아닙니다.

### 하이브리드(RRF)는 쓰지 않습니다

양쪽에서 중간입니다 — 어휘를 0.828 → 0.710 으로 깎고 의미도 0.042 → 0.032 으로
깎았습니다. **둘의 장점을 합친 게 아니라 서로를 끌어내렸습니다.**

원인은 RRF 가 **순위만 보고 확신도를 무시**하기 때문입니다. `백탁` 처럼 정확 일치가
명백한 질의에서도 벡터의 애매한 1위가 BM25 의 확실한 1위와 같은 무게(1/61)를
받습니다.

**대신 용도별로 갈라 씁니다.**

```
성분명 · SPF · 브랜드 (정확 일치가 정답)   →  BM25
"하얗게 떠서 싫다" (이름 없는 표현)         →  벡터
```

근거는 **합치는 게 아니라 나란히 놓는 것**입니다 — 소스를 합산하지 않은 것과 같은
논리입니다.

> 다만 `RRF_K = 60` 과 융합 깊이는 관행값이고 우리 데이터로 뽑지 않았습니다.
> 그 설정을 바꾸면 결론이 뒤집힐 수 있으므로 `ATTACK.md` 의 검토 항목에 넣었습니다.

### 성분 사전이 `literal` 을 깎았습니다 — 결함이 아니라 교환입니다

성분 사전을 얹으면서 `literal` 이 0.862 → 0.828 로 내려갔습니다. 원인을 찾았습니다.

| 질의 | 사전 전 | 사전 후 | 왜 |
|---|---:|---:|---|
| 옥토크릴렌 | 1.00 | **0.20** | 성분명이면서 유기자차 별칭 |
| 차단지수 | 1.00 | 0.40 | 같음 |
| PA | 1.00 | 0.60 | 같음 |
| 방수 | 1.00 | 0.80 | 같음 |

성분으로 등록되니 토큰화가 바뀌어 **성분 문서가 상위를 차지**합니다. 성분 청크는
`mention.csv` 에 없으니 정답이 아니어서 P@10 이 떨어집니다.

**얻은 것과 비교하면 남는 거래입니다** — 성분명 1,877종이 한 토큰으로 나오는 비율이
**41% → 100%** 가 됐습니다(1,108종이 살아남). 사전 없이는 `1,2-헥산다이올` 이
`['1', ',', '2', '-', '헥산다이올']` 로 쪼개져 **성분명 절반 이상이 검색 불가**였습니다.

그리고 잃은 쪽도 **틀린 게 아닙니다.** `옥토크릴렌` 을 치면 그 성분이 든 제품과
식약처 등록이 먼저 나오는 게 오히려 맞습니다. 담론만 원하면 `--per-source` 로
소스별로 봅니다.

### 소스별로 나눠 물어야 근거가 모입니다

전역 상위 k 를 쓰면 **다수 소스가 나머지를 덮습니다.** 색인 269,851개 중 유튜브
댓글이 247,086개(92%)고 평균 16토큰이라, BM25 의 길이 보정이 짧은 댓글을 밀어
올립니다. `판테놀 쓰는 선크림` 질의의 소스별 첫 등장이 이랬습니다.

```
  1위  youtube_comment
 37위  youtube_video
132위  formula_full
293위  mfds
(ingredient · formula_summary 는 300위 밖)
```

**점수가 틀린 게 아니라 묻는 방식이 틀렸습니다.** "무엇이 가장 관련 있나"가 아니라
"각 소스에서 무엇이 관련 있나"를 물어야 합니다. 소스 하나에서 근거를 다 뽑으면
교차 확인이 안 됩니다.

`--per-source` 로 물으면 이렇게 나옵니다.

```
[youtube_comment]  판테놀 무기자차 선크림 진리임..ᅲ
[youtube_video]    무너진 피부장벽 판테놀을 써야하는 이유
```

## 13. 이 파이프라인이 다섯 번 당한 것

같은 함정을 다섯 번 밟았습니다. **다섯 번 다 오류가 안 나고 결과가 그럴듯했습니다.**

| 언제 | 무엇이 관측값이 됐나 | 어떻게 알았나 |
|---|---|---|
| 수집 초기 | 채널당 **수집 상한 10** | 월별 집계가 매달 10건 근처 |
| 08.23 | **추출 방법** (정렬 없는 offset 페이징) | 현준님이 재현 안 된다고 알려줌 |
| 08.24 | **소스 비율** (색인 92%가 짧은 댓글) | 소스별로 나눠 물어보니 드러남 |
| 08.24 | **id 형식** (정답 `doc_id` vs 결과 `chunk_id`) | 벡터가 0.000 이 나와서 의심 |
| 08.24 | **문서의 명령** (`python` 이 스토어 스텁) | 붙여 넣었더니 `Python ` 만 찍힘 |

네 번째가 가장 아까웠습니다. 그대로 봤으면 **"임베딩은 이득이 없다"고 잘못 결론
내리고 발표했을 겁니다.** 벡터가 찾아온 상위 5건 중 3번째가 실제 정답인데 `#0` 이
붙어서 오답으로 세어졌습니다.

**그래서 자기 검사를 코드에 박습니다.** 문서에 적어 두는 것보다 낫습니다.

| 장치 | 어디 | 무엇을 막나 |
|---|---|---|
| 행수 대조 | `commerce_ranking.fetch` · `commerce_chunks.fetch` | 페이징 중 집합 변화 |
| 재현성 검사 | `reproduce.py` | 커밋 산출물이 지금 코드로 안 나오는 것 |
| 계약 검증기 | `chunks.py --validate` | 청크 위반 11종 |
| 기저율 병기 | `backtest.py` | 적중률만 내는 자기 홍보 |
| 캐시 키에 설정 해시 | `bm25.build` | 설정을 바꿔도 옛 색인을 쓰는 것 |
| 채택 기준 사전 고정 | `retrieval_eval` | 결과를 보고 기준을 만드는 것 |
| `--demo` | 거의 모든 스크립트 | 데이터 없이 로직이 죽은 것 |

**캐시 키에 설정을 빠뜨려 옛 결과를 쓴 실수를 두 번 했습니다**(`USER_WORD_SCORE`,
사전 해시). 새 손잡이를 만들면 캐시 키에도 같이 넣습니다.
