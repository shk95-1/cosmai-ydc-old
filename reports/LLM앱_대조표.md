# LLM 앱 두 개 숫자 대조표

> 2026.08.26 · 김시현 · 발표 전 리허설용
> 석현님 앱 · 현준님 DGX 앱 — 같은 질문에 다른 숫자가 나오면 발표장에서 문제가 됩니다.

---

## 왜 하나 — 이미 한 번 갈렸습니다

현준님 앱이 보던 행 수가 서버의 **절반**이었습니다(80,102 vs 173,007).
원인은 앱이 각자 다른 **사본**을 보고 있었기 때문입니다.

**그리고 지금 그 조건이 더 나빠졌습니다.** 서버가 계속 자라고 있습니다.

```
                 우리가 쓴 값      지금 서버 (08.26 측정)
rank_snapshot      202,258    →      251,683   (+24%)
review              19,807    →       27,230   (+38%)
```

**커머스 리뷰만 해도 세 숫자가 돕니다** — 우리 19,807(수집 시점) · 현준님
`review_key` 19,820 · 지금 서버 27,230. 필터와 시점이 다를 뿐 셋 다 맞습니다.

**같은 질문에 다른 답이 나오는 게 정상입니다.** 각자 다른 시점을 보고 있으면요.
그래서 대조의 목적은 "누가 맞나"가 아니라 **"어느 시점을 보고 있나"를 확인하는 것**입니다.

### D. 근거 추적 — 여기가 가장 크게 갈립니다

| # | 질문 | 기대 동작 | 석현님 앱 | 현준님 앱 | 판정 |
|---|---|---|---|---|---|
| 14 | 백탁이 문제라는 근거를 보여달라 | 원문을 **`doc_id`** 와 함께 제시 | | | |
| 15 | 백탁 리뷰가 몇 건인가 | **552건** (커머스 리뷰 청크 전수) | | | |

> **552 → 14 의 원인은 둘입니다** (현준님이 단계별로 분해해 주셨습니다).
>
> | source | 백탁 리뷰 | product 행 없음 | 조인됨·URL 없음 | 조인됨·URL 있음 |
> |---|---:|---:|---:|---:|
> | OliveYoung | 506 | 0 | **506** | 0 |
> | Glowpick | 46 | **32** | 0 | **14** |
> | 합계 | 552 | 32 | 506 | 14 |
>
> 제 초판은 *"올리브영 URL coverage 가 낮아서"* 하나로만 설명했는데 **불완전했습니다.**
> 올리브영 506행은 product 와 조인되지만 `url` 이 전부 비어 있고, glowpick 32행은
> URL 문제가 아니라 **대응하는 product 행 자체가 없어** 조인에서 사라집니다.
>
> 그리고 **두 552 는 세는 단위가 다릅니다.**
>
> ```
> 우리 552 = 커머스 청크 수 (리뷰 551건 + 백탁이 두 청크에 걸친 1건)
> 현준님 552 = public.review 행 수 (oliveyoung 506 + glowpick 46)
> ```
>
> oliveyoung **506 은 완전히 일치**합니다. glowpick 45 vs 46 의 1건 차이는
> `review_key 7860575` · `captured_at 08-24T01:00` — 현준님 스냅샷이 한 시간 더
> 봅니다. **제 초판 `505/45/기타 2` 는 플랫폼 판정 버그였습니다** — 접두어를
> `text[:26]` 에서 찾는데 이어지는 청크(`#1`)엔 접두가 없습니다.
>
> 결론은 그대로입니다 — `product.url` 은 계약상 **nullable** 이고
> `need_mention.ref` 는 **NOT NULL** 입니다(석현님). URL 은 결번이 허용된 컬럼,
> `doc_id`/`ref` 는 금지된 컬럼입니다. **285/6,083 은 사고가 아니라 설계의 결과입니다.**

## 4. 갈렸을 때 어떻게 읽나

| 증상 | 원인 | 대응 |
|---|---|---|
| 행 수만 다르다 | 시점이 다르다 | **정상.** 발표에서 시점을 붙여 말한다 |
| 성분 제품 수가 375/374 | 복구 전 CSV | 그 앱의 소스를 31,246행 판으로 교체 |
| 논문 숫자를 답한다 | 철회 반영 안 됨 | **발표 전에 막아야 한다** |
| 예측을 답한다 | 가드레일 없음 | **발표 전에 막아야 한다** |
| 근거 없이 숫자만 답한다 | 원문 링크 미구현 | 발표에서 그 질문을 피하거나 한계로 밝힌다 |

**빨간 줄 둘**: 논문 숫자와 예측입니다. 나머지는 시점을 밝히면 넘어갑니다.

## 5. 발표 중 안전한 표현

```
"2026-08-19 수집분 기준으로 선크림 장문 964편, 댓글 60,311건입니다"
"서버는 계속 쌓이고 있어서 지금은 더 많습니다"
"논문 축은 검증 프로토콜이 나올 때까지 쓰지 않습니다"
"이건 예측이 아니라 지금 이런 비대칭이 있다는 관측입니다"
```

**석현님이 더 좋은 방법을 주셨습니다** — 날짜 대신 `run_id` 를 말하는 것입니다.
`needs.analysis_run(run_id, started_at, versions jsonb)` 에 linker·extractor·
polarity·aggregate·lexicon 판이 함께 남습니다. **시점뿐 아니라 어느 판의 사전·
추출기로 뽑았는지까지 한 번에 고정**됩니다. 우리 쪽 동등물은 커밋 해시입니다.

**그리고 하나 더 확인할 것** — `review_pkey` 가 `(source, review_key)` 입니다.
리뷰의 정체성이 `review_key` 단독이 아닙니다. 우리 19,807 과 현준님 19,820 의
13건 차이는 위 백탁 화해와 같은 계열(경계 시각)로 보이지만, **세는 단위를
`(source, review_key)` 로 맞춰 한 번 더 확인할 값어치가 있습니다.**

**"우리 숫자가 맞다"고 하지 않습니다.** 시점을 말하면 둘 다 맞습니다.
