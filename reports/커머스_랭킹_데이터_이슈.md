## 0. 정정 — 제가 틀렸습니다

초판에서 두 가지를 보고드렸는데 **둘 다 서버에 없는 현상**이었습니다.

| 초판 주장 | 사실 |
|---|---|
| 완전 중복 62,812행 (37%) | **중복 0건** |
| 스냅샷 관측 깊이 22~100위로 들쭉날쭉 | **보드 22개 중 21개 깊이 고정.** oliveyoung suncare 는 85개 스냅샷 전부 100위 |

**원인은 제 추출 코드입니다.** PostgREST 에서 `limit/offset` 페이징을 했는데
**`ORDER BY` 를 아예 넣지 않았습니다.** Postgres 는 정렬을 지정하지 않으면 순서를
보장하지 않고, 그 위에 수집기가 계속 쓰고 있었습니다. 그래서 같은 offset 이
다른 행을 가리켰습니다.

- 같은 행이 여러 번 들어옴 → **중복으로 보임**
- 다른 행은 통째로 빠짐 → 스냅샷이 얕게 보임 → **깊이 변동으로 보임**

**현준님이** 자기 사본(173,007행)에서 재현이 안 된다며 이 가설을 먼저 제기해
주셨습니다(정렬 키가 `source` 로 시작하면 새 daisomall 행이 중간에 꽂혀 뒤가
밀린다는 지적). 확인해 보니 맞았습니다.

### 어떻게 확인했나

**① 지목한 슬라이스를 직접 조회했습니다.** 초판에서 중복 예시로 든 그 행입니다.

```
GET /rank_snapshot?source=eq.oliveyoung&board=eq.masks
  &category_key=eq.10000010009&captured_at=eq.2026-08-23T17:00:00+00:00&rank=eq.51
→ 1행
```

**② 정지 집합을 정렬해 다시 받았습니다.**

```
captured_at < 2026-08-24T00:00:00+00:00
order = captured_at, source, board, category_key, rank, product_key
→ 서버 count=exact 169,053 · 받은 행수 169,053 (일치)
→ 완전 중복 0건
→ 보드 22개 중 깊이 고정 21개 (변동은 daisomall sale_rising 92~100 한 보드뿐)
```

### 초판의 "증거"가 왜 그럴듯했나

초판에서 이 두 가지를 원인 추정의 근거로 들었는데, **둘 다 페이징 표류로 더 잘
설명됩니다.** 현준님이 지적한 대로입니다.

| 제가 든 근거 | 초판 해석 | 실제 |
|---|---|---|
| 08.18~19 는 0건, 08.20부터 증가 | 08.20 에 들어간 코드 변경 | **수집량이 537 → 25,272행/일로 뛴 날.** 유입이 많을수록 표류가 큼 |
| 네 소스가 정확히 37%씩 | 공통 적재 경로 문제 | **표류는 스트림 전체에 균일하게 걸림.** 수집기 버그면 소스마다 달랐을 것 |

**"네 소스가 똑같이 37%" 를 저는 공통 원인의 증거로 읽었는데, 그게 오히려 제
추출이 원인이라는 증거였습니다.** 수집 파이프라인 버그라면 소스마다 값이
달라야 합니다.

### 고친 것

`commerce_ranking.py` 의 `fetch` 에 세 가지를 걸었습니다.

1. `captured_at < freeze` 로 작업 집합 **정지**
2. 유일 키로 **전순서 정렬**
3. 받은 행수를 서버 `count=exact` 와 **대조하고 어긋나면 중단**

3번이 핵심입니다. 정지·정렬만 해도 대개 맞지만, **행수를 대조하지 않으면 다음에
또 조용히 틀립니다.** 초판에서 제가 그걸 안 했습니다.

### 결론이 어떻게 바뀌나

보정을 "아티팩트 제거"로 설명한 것도 철회합니다. 깊이가 고정이므로 **올리브영
선케어 100위권은 실제로 크게 움직입니다.**

| oliveyoung 선케어 | 100위권 전체 | 상위 20위만 |
|---|---:|---:|
| 제품 | 380 | 82 |
| 중앙 변동폭 | **38계단** | **8계단** |
| 움직임 없음 | 13% | 11% |
| 신규 진입 | 111 | 23 |

상위 20위로 좁히는 것은 여전히 의미가 있지만, **아티팩트를 걷어내는 게 아니라
관심 구간을 고르는 것**입니다. 100위권의 큰 변동은 진짜입니다 — 프로모션·기획
상품이 랭킹을 밀어 올리는 구조로 보입니다.

실제 이동입니다.

```
상위 20위 안       18 → 4  닥터지 브라이트닝 업 선 플러스
                  20 → 7  제로이드 이지워시 마일드 선크림
                   1 → 15 오브제 포어 제로 오일 컨트롤 선스틱

100위권 전체       75 → 16 브링그린 알로에 97% 수딩젤
                  14 → 100 아누아 제로캐스트 수분 선크림
```

**석현님 수집기는 문제가 없었습니다.** 두 분 시간 쓰게 해서 죄송합니다.
현준님이 재현 안 된다고 바로 알려주지 않았으면 잘못된 숫자로 발표했을 겁니다.

## 3. daisomall 카테고리가 한 덩어리입니다

`category_name` 이 **`뷰티/위생` 하나뿐**입니다(34,677행). 다른 소스는 이렇게 옵니다.

```
oliveyoung   01 > 선케어 > 선블록        8,241행
glowpick     선크림
hwahae       페이셜클렌저
daisomall    뷰티/위생                 34,677행   ← 더 잘게 없음
```

그래서 **daisomall 은 선케어 분석에서 통째로 빠집니다.** hwahae 도 선케어 분류가 없어 빠집니다(보드가 trending·category·skin·age 로만 나뉩니다).

지금 선케어 시계열은 oliveyoung(6,480행) + glowpick(1,082행) 둘로만 됩니다.

다이소가 저가 선케어에서 존재감이 있으니 카테고리를 더 잘게 받을 수 있으면 값이 있습니다. 안 되면 **제품명 매칭으로 선케어를 추려야 하는데, 그건 정확도가 떨어지므로 미리 합의가 필요합니다.**

## 5. 저희가 이미 우회한 것

- 추출은 **정지 + 전순서 정렬 + 행수 대조**로 바꿨습니다. 대조가 어긋나면 멈춥니다
- 중복 제거 함수는 남겼습니다 — **0 이 아니면 추출이 잘못됐다는 신호**로 씁니다
- 깊이 보정도 남겼습니다. 지금은 거의 무동작이지만 보드별 목표 깊이가 달라
  (glowpick 20 · hwahae 9 · 나머지 100) 비교 구간을 맞추는 일 자체는 필요합니다
- 100위권 전체와 상위 20위 결과를 둘 다 냅니다 — 이제 "아티팩트 제거"가 아니라
  **관심 구간 선택**입니다

```bash
python commerce_ranking.py            # 서버에서 받아 캐시하고 분석
python commerce_ranking.py --offline  # 캐시만
python commerce_ranking.py --depth 10 # 보정 기준 순위 변경
```

## 6. 덧붙여 — 랭킹이 6일치가 된 게 발표에 주는 영향

시간축을 가진 소스가 **둘에서 셋**이 됩니다.

| 소스 | 시간축 | 무엇을 보나 |
|---|---|---|
| 식약처 | 18년 | 공급측 — 제조사가 무엇을 언제 내놨나 |
| 유튜브 | 13분기 | 수요측 담론 — 무엇이 더 논의되나 |
| **커머스 랭킹** | **6일 · 시간당** | **성과 — 무엇이 지금 순위에 오르나** |

다만 **6일로 분기 트렌드는 못 봅니다.** 유튜브 지표는 전년 동분기 비교이고 계절성을 상쇄하려고 그렇게 만들었습니다. 커머스 6일에 같은 규칙을 쓰면 의미가 없습니다. 커머스로 볼 수 있는 건 **주간 순위 변동**이고, 이건 "지금 무엇이 오르고 있나"라는 다른 질문입니다.

수집기가 계속 돌고 있으니 발표일(08.26)에는 8일치가 됩니다. 정지 시각만 그때로 바꾸면 됩니다. MASTER_REPORT §9 의 "랭킹 스냅샷 추가 수집 → 지속성 지표 계산 가능해짐" 항목이 실제로 가능해졌습니다.
