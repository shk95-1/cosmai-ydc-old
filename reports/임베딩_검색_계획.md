| | |

## 1. 나눠서 임베딩하면 안 되는 이유 — 방식에 따라 갈립니다

### TF-IDF / SVD 는 나눌 수 없습니다

`step05_evidence.py` 가 쓰는 TF-IDF + SVD 는 **코퍼스에 학습되는** 방식입니다. 어휘 목록과 IDF 가중치, SVD 축이 전부 "넣은 문서 전체"에서 나옵니다.

두 사람이 각자 fit 하면 **코드가 완전히 똑같아도 서로 다른 좌표계**가 나옵니다. 그 두 벡터 사이의 코사인 유사도는 숫자는 나오지만 의미가 없습니다. 오류도 안 납니다 — 그냥 조용히 엉뚱한 검색 결과가 나옵니다.

### 사전학습 모델은 나눌 수 있습니다

문서 하나하나를 독립으로 인코딩하므로, 나중에 이어 붙이면 그게 곧 전체입니다. **단 아래 6개가 전부 같아야 합니다.**

| 못 박을 것 | 어긋나면 |
|---|---|
| 모델 이름 **+ 리비전 해시** | 갱신본이 내려오면 다른 벡터가 나옵니다. 이름만으로는 부족합니다 |
| 프리픽스 규칙 | e5 계열은 `query: ` / `passage: ` 필수. **에러 없이 성능만 떨어집니다** |
| L2 정규화 여부 | 한쪽만 하면 유사도 스케일이 달라 순위가 섞입니다 |
| 차원 · dtype | float32 고정. float16 저장본과 섞으면 미세하게 어긋납니다 |
| 텍스트 정규화 | `trend.normalize_text` 하나만 씁니다 (이미 팀 합의된 규칙) |
| 어느 필드를 넣는지 | 유튜브에서 태그를 뺀 것과 같은 결정입니다. 소스마다 기록해야 합니다 |

### 결론

**사전학습 모델로 가고, 그래도 인코딩은 한 번에 돌리는 게 낫습니다.**

이유는 속도입니다. 전체가 유튜브 26만 + 커머스 1.5만 + 논문 + NAVER 이고, 사전학습 모델로 GPU 에서 돌리면 **10~30분**입니다. 나눠서 얻을 시간이 없는데 합치기 위험만 생깁니다.

## 2. 그래서 이렇게 나눕니다

| 단계 | 담당 |
|---|---|
| 소스별 **청크 만들기** — 뭘 한 덩어리로 볼지, 어느 필드를 넣을지 | **나눔** (각자 자기 소스) |
| 인코딩 1회 | **한 사람이 전체** |
| 검색·평가 | 나눔 |

각자 같은 형식의 파일 하나만 내면 됩니다.

```
chunks.csv
  chunk_id, doc_id, source, ordinal, text
```

`doc_id` 는 우리 5계층 공통 스키마의 그것을 씁니다. 그러면 합치는 게 **join 이 아니라 그냥 이어 붙이기**가 됩니다 — 합칠 게 없으니 못 합칠 일도 없습니다.

### 청크 규칙이 진짜 일입니다

소스마다 "한 덩어리"의 정의가 다릅니다. 이건 그 소스를 아는 사람만 정할 수 있습니다.

| 소스 | 제안 |
|---|---|
| 유튜브 댓글 | 1건 = 1청크 (평균 20토큰, 쪼갤 게 없음) |
| 유튜브 영상 설명 | 500자 넘으면 분할 (설명란 중앙 709자, 최대 5,000자 이상) |
| 커머스 리뷰 | 1건 = 1청크 |
| **성분표** | **여기가 수호님 판단이 필요합니다** — 아래 참조 |
| 식약처 원부 | 1품목 = 1청크 (효능효과 원문 + 품목명) |
| 논문 | 초록 / 본문 절 단위로 분리 |

**성분표 청크가 까다롭습니다.** 30,097행이 (제품 × 성분) 이라 행 하나를 청크로 만들면 `정제수` 청크가 577개 생깁니다. 세 가지 선택지가 있습니다.

1. **제품 단위** — 577청크. 전성분을 한 문장으로 이어 붙임. 검색은 "이 조합의 제품"을 찾는 데 강함
2. **성분 단위** — 1,949청크. 성분 하나 + 그걸 쓴 제품 목록. "이 성분을 쓰는 제품" 검색에 강함
3. **둘 다** — 2,526청크. 용량이 작으니 비용 문제는 없음

제 의견은 **3번**입니다. 카드가 두 방향을 다 물어봅니다 — "혼합자차 제품이 뭐가 있나"(제품 단위)와 "판테놀 쓰는 제품이 몇 개나 되나"(성분 단위). 청크 2,526개는 유튜브 26만 대비 1% 라 비용이 없습니다.

## 3. 모델 제안

**`intfloat/multilingual-e5-base`**

| | |
|---|---|
| 한국어 | 됩니다 |
| 차원 | 768 |
| 프리픽스 | `query: ` / `passage: ` **필수** |
| 최대 길이 | 512 토큰 (그래서 청크 분할이 필요합니다) |
| 무게 | 가볍습니다. GPU 없어도 26만 문서가 한 시간 안에 끝납니다 |

성분명·제형 용어 같은 **정확 일치**가 더 중요하다고 판단되면 `BAAI/bge-m3` 가 낫습니다(8,192토큰, dense+sparse 동시 출력). 다만 무겁고, 정확 일치는 아래 BM25 가 이미 담당합니다.

**리비전 해시를 반드시 같이 적어야 합니다.** `intfloat/multilingual-e5-base` 만 쓰면 나중에 갱신본이 내려와도 이름이 같습니다.

## 4. 벡터만으로는 안 됩니다 — BM25 를 먼저 만들었습니다

MASTER_REPORT §4 에 이미 답이 있습니다 — *"한국어 어미가 벡터 검색을 지배(`~해요`) → 하이브리드 검색(어휘 50% + 의미 50%)으로 전환"*. 저희도 같은 결론이고, 그래서 **어휘 쪽을 먼저 만들었습니다.**

### 둘이 반대로 약합니다

```
질의: "에칠헥실트리아존"
  BM25 → 그 문자열이 있는 문서를 정확히 찾는다
  벡터 → "화학 성분 이름 같은 것"이랑 다 비슷하다고 본다
         (에칠헥실메톡시신나메이트도 비슷하다고 나옴 — 성분이 다른데)

질의: "하얗게 떠서 싫다"
  BM25 → 못 찾는다. "백탁"이라는 글자가 없다
  벡터 → 찾는다. 뜻이 가깝다
```

**성분 검색은 특히 어휘 쪽이 필수입니다.** 수호님 데이터가 여기 해당합니다.

### 실측 — BM25 가 이미 동작합니다

유튜브 26만 문서 색인, 질의 `"하얗게 떠서 싫다"` 상위 5건:

```
15.393  데오도란트 하얗게 되는거 싫어서 안뿌리고 있었는데!
13.732  수정화장할때 하얗게 뜬 경우에는 어케 하나용
13.698  무기자차 선크림만 바르면 하얗게 뜨는 분들은 참고!
13.327  선크림 한 번만 발라도 얼굴이 하얗게 떠서 두 번 바르기가 쉽지 않네요
13.327  땀나도 하얗게 안뜨나요?
```

다섯 건 모두 백탁 얘기이고, **다섯 건 모두 "백탁"이라는 단어가 없습니다.** 우리 주제 사전이 `하얗게` 를 별칭으로 갖고 있어서 잡힌 경우입니다.

### 만들면서 걸린 함정 다섯 개 — **성분표에서 같은 문제가 납니다**

다섯 개 모두 **에러가 안 납니다.** 검색 결과가 조용히 비어서 나옵니다. 그래서 평가기를 먼저 만들어야 발견됩니다 — 저희도 P@10 이 0.754 로 나와서 알았습니다.

**① Kiwi 태그에 불규칙 표시가 붙습니다.** `하얗` 의 태그가 `VA` 가 아니라 **`VA-I`** 입니다. 태그 집합으로 필터하면 형용사·동사가 전멸합니다. `"하얗게 떠서 싫다"` 의 질의 토큰이 **0개**로 나왔습니다. 하이픈 앞만 봐야 합니다.

**② 한 글자 필터를 서술어에 걸면 안 됩니다.** 한 글자 명사(`것`·`거`·`수`)는 잡음이지만 **서술어 어간은 한 글자가 정상**입니다 — `하얗`·`뜨`·`싫`·`시리`. 명사에만 길이 조건을 걸어야 합니다.

**③ 사전은 부분문자열, 색인은 형태소 — 단위가 어긋납니다.** 이게 근본 원인입니다.

```
신제품   → ['제품']        신 이 접두사로 떨어진다
화학적   → ['화학']        적 이 접미사로 떨어진다
차단지수 → ['차단','지수']  둘로 갈린다
제형     → []             제(접두) + 형(한 글자) 로 전멸한다
```

`제형` 이 빈 결과인 건 평가 문제가 아니라 **검색 결함**입니다. 사용자가 "제형"을 치면 아무것도 안 나옵니다.

**성분명이 정확히 이 문제에 걸립니다.** `에칠헥실트리아존` 을 Kiwi 가 어떻게 쪼개는지 **반드시 먼저 찍어보셔야** 합니다. 쪼개지면 성분 검색이 조용히 안 됩니다.

**④ `add_user_word` 에 score 를 줘야 합니다.** 기본값 0 으로 등록하면 **등록해도 무시됩니다.** `신제품` 을 등록했는데 여전히 신(XPN)+제품(NNG) 으로 갈렸습니다. 저희는 3.0 을 줬습니다.

**⑤ 활용형을 명사로 등록하면 형태소 통합이 깨집니다.** 반대 방향 함정입니다. `하얗게`·`하얘` 를 명사로 넣으니 서로 다른 토큰이 됐습니다 — 등록 전에는 둘 다 `하얗` 으로 합쳐졌습니다. 그래서 **등록 대상을 손으로 정하지 않고 Kiwi 에게 물어서** 고릅니다.

```
등록 21개   Kiwi 가 쪼개고 + 서술어 읽기가 없는 것만
            제형 · 신제품 · 화학적 · 차단지수 · 피부톤 · 메이크업베이스 ...
제외        활용형이므로 통합을 살린다
            하얗게 · 하얘 · 따갑 · 붉어 · 밀려 · 뭉침 · 무너짐 ...
```

**등록과 확장은 다른 집합입니다.** 등록은 "Kiwi 가 쪼개니 붙여 달라", 확장은 "Kiwi 가 온전히 주는데 그 안에 별칭이 있다"(`끈적임` → `끈적` 도 같이 냄). 섞으면 둘 중 하나가 망가집니다.

## 5. 평가는 이렇게 합니다 — 정답을 만드는 게 문제입니다

세 겹입니다.

### 평가 1 — 사전 라벨 자동 채점 (정답이 공짜)

`common/mention.csv` 에 (문서, 주제) 105,358쌍이 이미 있습니다. `match_topics()` 가 만든 것이라 사람이 라벨을 달 필요가 없습니다.

두 모드로 재고, **둘이 서로 다른 질문**입니다.

| 모드 | 질의 | 정답 | 목적 |
|---|---|---|---|
| `literal` | 별칭 하나 (`백탁`) | 그 주제 문서 전부 | **고장 감지.** 정답이 문자열 매칭으로 만들어졌으니 BM25 가 당연히 잘합니다. 여기서 못하면 토큰화가 깨진 것입니다 |
| `heldout` | 별칭 A (`하얗게`) | **A 의 토큰이 하나도 없는** 같은 주제 문서 | **진짜 측정.** BM25 는 여기서 거의 0 이 정상이고, **그 0 이 벡터가 넘어야 하는 선입니다** |

`heldout` 에서 후보 문서를 줄이지 않는 게 중요합니다. 두 방식이 **같은 후보·같은 정답**으로 경쟁해야 점수를 비교할 수 있습니다.

지표는 P@10 · Hit@10 · MRR@10 입니다. 정답 집합이 수천~수만이라 Recall@10 은 정의상 0.1% 를 못 넘어 쓸 수 없습니다.

**실측 결과 (유튜브 26만 문서, 질의 61개)**

| 모드 | P@10 | MRR@10 | Hit@10 |
|---|---:|---:|---:|
| `literal` (고침 전) | 0.754 | 0.799 | 87% |
| `literal` (고침 후) | **0.862** | **0.907** | **93%** |
| `heldout` | **0.000** | 0.000 | 0% |

`literal` 이 아직 0.9 밑인데, 남은 12개 질의는 세 갈래로 나뉩니다.

| 갈래 | 예 | 판단 |
|---|---|---|
| 낱말이 아닌 별칭 | `눈 시림` · `톤 업` · `땀에` | **평가 쪽 문제.** 실제 질의가 아니고 부분문자열 사전에서만 의미가 있습니다 |
| 코퍼스에 거의 없는 별칭 | `재도포`(2건) · `차단지수`(23건) | **표본 부족.** 채점이 불가능합니다 |
| 형태소가 사전보다 넓음 | `하얗게`(0.5) | **결함이 아닙니다.** `하얀`·`하얗다` 도 `하얗` 으로 잡혀서 사전이 놓친 문서까지 가져옵니다 |

세 번째가 재미있는 결과입니다. 감점처럼 보이지만 **검색기가 사전보다 넓게 찾고 있다**는 뜻입니다.

**`heldout` 이 0.000 인 것은 측정이 아니라 정의입니다.** 정답을 "질의 토큰이 하나도 없는 문서"로 잡았으니, 토큰이 겹치는 문서만 점수를 매기는 어휘 검색은 **구조적으로 0** 입니다. 그래서 이 숫자는 발견이 아니라 **바닥선**입니다 — 벡터가 0 을 넘기면 그게 곧 임베딩이 기여한 몫이고, 못 넘기면 붙일 이유가 없습니다.

### 평가 2 — 사람이 만든 골든셋 (벡터의 진짜 가치)

사전이 **놓친** 문서를 벡터가 건져 오는지가 임베딩을 붙이는 이유 전부입니다.

```
질의   "발랐을 때 하얗게 뜨는 게 싫다"     ← 사전에 없는 표현
필터   match_topics 가 아무것도 못 붙인 문서만
판정   상위 10건을 사람이 보고 맞는지 표시
```

**각자 자기 소스에서 질의 5개**만 만들면 됩니다. 20개 × 10건 = 200건 판정이면 30분입니다.

| 사람 | 질의 예 |
|---|---|
| 시현 (유튜브) | "발림성 불만", "눈 시린다", "하얗게 뜬다" |
| **수호 (성분·식약처)** | **"무기 자외선차단제 성분", "진정 성분이 실제로 들어간 제품"** |
| 석현 (커머스) | "가격 대비 아쉽다", "재구매 의사" |
| 현준 (NAVER·논문) | "차세대 UV 필터", "광안정성" |

### 평가 3 — 근거 추적 (기획안 08.24 요구 항목)

기획안 08.24 가 *"RAG 근거·원문 추적 검증"* 입니다. 검색 품질이 아니라 **거짓말 안 하는지**를 잽니다.

| 검사 | 통과 기준 |
|---|---|
| 문장의 **숫자**가 근거 문서나 우리 CSV 에 실제로 있나 | **100%** |
| 문장에 인용된 **표현**이 원문에 n-gram 으로 있나 | **100%** |
| 인용한 문서 id 가 실재하나 | **100%** |

90% 가 아니라 100% 여야 합니다. 하나라도 실패하면 그 문장을 생성 단계에서 막습니다. 팀 원칙 — **숫자는 코드, 문장만 LLM** — 을 실제로 강제하는 장치입니다.

### 규칙 하나 — 평가 세트를 오염시키지 않기

**평가 1(자동)로 가중치를 고르고, 평가 2(골든셋)는 마지막에 한 번만 씁니다.** 골든셋을 보면서 파라미터를 만지면 그 숫자는 성능이 아니라 우리가 맞춘 결과가 됩니다.

같은 이유로 후향 검증에서 기저율을 같이 냈습니다 — 적중률만 내는 검증은 검증이 아니라 홍보입니다.

## 7. 주의사항 두 개

**① 인덱스에는 원문이 그대로 들어갑니다.** 저희가 `evidence_comments.csv` 와 대시보드를 깃에서 뺀 이유(기획안 §4 — 원문은 분석 목적 범위에서만 보관, 재배포하지 않음)가 인덱스에도 똑같이 적용됩니다. **인덱스 파일은 깃에 올리지 않고 생성 스크립트로 재현**하는 쪽으로 가야 합니다.

**② 논문이 영어면 갈라집니다.** Kiwi 는 한국어 전용입니다. 토큰화에 언어 분기 자리를 이미 만들어 뒀습니다(한글 5% 넘으면 한국어). 다만 질의도 갈라지므로 — "차세대 UV 필터"로 영어 논문을 찾으려면 — **논문 검색은 벡터 비중이 커집니다.** 그리고 우리 주제 사전은 소비자 표현(`백탁`·`눈시림`)으로 만들어져서 논문 초록(`whitening effect`·`photostability`)에는 거의 안 걸립니다. 평가 1 의 자동 라벨이 논문에서는 안 생기므로 논문은 평가 2 로만 봐야 합니다.

## 8. 수호님께 여쭙고 싶은 것

1. **모델** — `intfloat/multilingual-e5-base` 로 가도 괜찮을까요? 다른 의견 있으시면 그쪽으로 맞추겠습니다. 중요한 건 **하나로 통일**하는 것입니다.
2. **성분표 청크** — 제품 단위 / 성분 단위 / 둘 다 중 어느 쪽이 좋을까요? 저는 둘 다(2,526청크)를 제안드립니다.
3. **식약처 원부** — 저희가 아직 원본을 못 받았습니다. 받으면 `data/external/` 에 매니페스트와 함께 두겠습니다.
4. **질의 5개** — 성분·식약처 쪽에서 R&D 질문 형태로 5개 부탁드립니다.

### 곁들여 — 성분 CSV 정본을 정해야 합니다

`step06_ingredient.py` 와 저희 `normalize_ingredients.py` 가 같은 파일을 각자 정규화했습니다. **데이터는 같습니다** — 원본 30,097행 / 577제품 / 207브랜드로 MASTER_REPORT 숫자와 정확히 일치합니다. 저희 30,345행은 뭉친 행 6개를 분해해 248행 늘어난 것이고 제품 수는 같습니다.

그래도 정규화 규칙이 갈라지면 "성분 몇 종" 같은 숫자가 발표 자료 안에서 두 개가 됩니다. `step06` 이 DB 파이프라인의 일부이고 저희는 축 분류용으로만 쓰므로, **`step06` 을 정본으로 두고 저희가 갈아타는 쪽**이 맞다고 봅니다.


|---|---|

첫 색인은 26만 문서 Kiwi 형태소 분석에 **4~5분** 걸리고, 이후는 캐시에서 **4초**입니다. 토큰화 규칙을 고치면 캐시가 자동으로 무효가 됩니다.

**커머스·논문·NAVER 가 공통 스키마로 변환되면 이 코드는 안 바뀝니다.** `document.csv` 에 행이 늘어나는 것뿐입니다. 소스마다 필요한 건 변환기와(NAVER 는 간단합니다) 청크 규칙입니다.
